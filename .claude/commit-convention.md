# 커밋 컨벤션

이 저장소(Winapi-btd-5)는 별도의 브랜치 전략 없이 **`main` 브랜치에서 바로 작업/커밋**합니다.
커밋을 생성할 때는 이 문서의 규칙을 따르세요.

## 브랜치 전략

- `main` 브랜치 하나만 사용합니다. `feature/*`, `develop` 등 별도 브랜치를 만들지 않습니다.
- 모든 커밋은 `main`에서 바로 만듭니다.

## 커밋 메시지 형식

```
<type>: <subject>

<body: 진행한 내용을 1. 2. 3. ... 번호 목록으로 요약 (개수는 진행한 내용 수에 맞게 늘어나도 됨)>
```

- `subject`(설명)는 세부 내용이 아니라 **큼지막하게(상위 개념으로) 한 줄 요약**합니다. 자세한 내용은 subject가 아니라 body에 적습니다.
- `body`는 해당 커밋에서 진행한 내용을 `1.` `2.` `3.` ... 번호 목록으로 정리합니다. 항목 개수는 4개로 고정이 아니라, 진행한 내용이 많으면 그만큼 늘려서 작성합니다.
- body의 각 항목은 "무엇을 했다"로 끝내지 말고, **어떤 과정으로/왜 그렇게 했는지까지 최대한 자세히** 적습니다. (예: 단순히 "리팩터링함"이 아니라 "A가 B를 직접 참조하던 구조를, C 델리게이트를 통해 간접 호출하도록 바꿔서 의존성을 끊음") body는 자세할수록 좋습니다.
- 새로 만든 함수/클래스가 있다면 **왜 만들었는지(어떤 문제를 해결하려고, 또는 어떤 미래 용도를 위해 만들었는지)**도 함께 적습니다. 지금 당장 호출하는 곳이 없는 함수라면 "지금은 미사용이며, 이후 ~할 때 쓰려고 미리 만들어둠"처럼 미사용 상태와 만든 의도를 명시합니다.
- **Co-authored-by 트레일러는 절대 추가하지 않습니다.**

### type 목록

| type | 의미 |
|---|---|
| `feat` | 신규 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |ㄴ
| `style` | 포맷팅 등 코드 의미에 영향 없는 변경 |
| `docs` | 문서 변경 |
| `test` | 테스트 추가/수정 |
| `chore` | 빌드, 설정 등 기타 잡무 | 
| `perf` | 성능 개선 |
| `revert` | 이전 커밋 되돌리기 |

### 예시

```
feat: CollisionManager 신설

1. RenderLayer 쌍 등록(RegisterLayer) 기능 추가
2. 등록된 레이어끼리 매 프레임 충돌 판정(checkLayer) 구현
3. 충돌 감지 시 양쪽 Actor::OnEnter 호출
4. TowerDefense.vcxproj/.filters에 신규 파일 등록
```

## 주의사항

- Co-authored-by 등 작성자 관련 트레일러를 커밋 메시지에 넣지 않습니다.
- description(제목)은 장황하게 쓰지 않고 큼지막한 한 줄 요약으로 남깁니다.
- body는 항상 번호 목록(1. 2. 3. ...) 형식으로 작성하며, 개수는 내용에 맞게 조절합니다.
- 사용자가 "커밋해줘"라고 요청할 때마다 이 문서를 먼저 읽고 규칙을 적용합니다.
